## Blocking Issues

### Issue 1 — Warn Findings to Stdout (cli-entry.ts:200-204)

**Specification:** Spec §2.3 states "warn → 0 (warnings to stderr)"

**Implementation:** Both branches of `_renderFinding` use `console.log` (stdout):
```typescript
if (f.source === 'system') {
  console.log(`${prefix} ${f.label} — ${f.message}`);  // ← stdout
} else {
  console.log(`${prefix} ${f.message}`);               // ← stdout  
}
```

**Comment contradiction:** The comment immediately above `process.exit(2)` says "Warnings go to stderr" — directly contradicting the implementation.

**Impact:** Piped tooling cannot distinguish warnings from info output. Spec contract is violated.

**Fix scope:** Replace `console.log` with `console.error` or `process.stderr.write()` for `f.severity === 'warn'`.

### Issue 2 — Missing Unified Severity Escalation Test

**Specification:** Spec §5 "New Tests Needed" section states:
> "A test where system doctor produces a `warn` and registry doctor produces an `error` → overall exit code is 2."

This scenario is described as the **core behavioral claim of the unification** (cross-source severity escalation).

**Current test coverage:** Five new tests added:
- Source grouping (system vs registry findings)
- passCount field assertion  
- Empty findings edge case
- Error finding shape validation
- (one more coverage test)

All 5 tests run against a **healthy scaffold** that produces zero errors. None exercises the scenario where different sources produce different severities that must be escalated.

**Impact:** The most critical piece-22 behavior (escalation logic) is untested. A regression that breaks escalation would pass the test suite.

**Fix scope:** Add one test scenario to `test/cli/doctor.test.ts` that:
- Stubs system doctor to return warn-severity findings
- Stubs registry doctor to return error-severity findings  
- Asserts `runUnifiedDoctor` returns findings with at least one error-severity
- Asserts caller's exit-code derivation would yield `process.exit(2)`

Estimated: ~15 lines of test code.

## Pattern Learning

**Warn-to-stderr contracts:** When a spec uses the phrase "warn → N (warnings to stderr)", verify BOTH:
1. The exit code derivation (correct in this case)
2. The stream routing in the renderer (incorrect in this case)

These are independent concerns. A code comment saying "warnings go to stderr" is not the same as `console.error()`. Always grep for `console.log` calls in severity-keyed render helpers.

The contradiction is instructive: Flight wrote the correct comment but implemented the wrong code path — a reminder that review must verify implementation against specification, not against developer intent expressed in comments.
