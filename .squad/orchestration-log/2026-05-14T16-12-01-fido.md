## Blocking Findings

### 1. Consult Setup-Mode Resolver-Success Path Unexercised

**Severity:** BLOCKING

The spec requires fixture coverage showing the resolver succeeds and "each user-action command reaches its normal command-specific behavior." The only consult success test exercises `--status`, which explicitly bypasses the resolver guard by design. **The guarded setup-mode path is never exercised in the success direction.**

- No test calls `squad consult` (no flags) from a registered consumer repo
- No assertion that config is written post-resolution
- Pattern violation: spec fixture mandate not met

### 2. `.gitignore` Non-Mutation Unverified for Consult+Link Failure Paths

**Severity:** BLOCKING

The spec explicitly requires: "does not append to .gitignore" and "resolver failure does not create consult files or ignore entries." Both tests check only `config.json`. **A regression that writes a `.gitignore` entry before a guard exit would be completely missed.**

- `runConsult` may touch `.gitignore` or `.git/info/exclude` before secondary guard
- `runLink` explicitly appends `.gitignore` on success; early-exit bug in guard could reach write
- Test fixture cleanup would remove the evidence post-test
- No assertion for failure path safety

### 3. Three Assign-to-Copilot Spec-Required Failure Modes Not Implemented

**Severity:** BLOCKING (scope under-delivery)

The spec test surface explicitly lists:
- URL-without-clone-destination failure
- Clone failure
- Host verification failure

**None of these exist in the `assign.ts` implementation.** The command registers a cwd as a clone but has:
- No URL-handling
- No git clone operation
- No host-repo verification

This is an **under-delivered scope item**, not a deferred-feature deferral. The spec does not mark these as "Out of scope"; they are required by the test surface.

### 4. Dead `resolved` Variable in Consult and Link Dispatch Blocks

**Severity:** BLOCKING (subtle divergence risk)

- `cli-entry.ts:1010–1019` (consult): `const resolved = resolveSquadV2(...)`, then `runConsult(getSquadStartDir(), args.slice(1))` WITHOUT the `resolved` value
- `cli-entry.ts:1042–1055` (link): `resolved = resolveSquadV2(...)` computed and null-checked, then `runLink(getSquadStartDir(), teamPath)` called without it

**If runners re-resolve internally**, the guard and runner can diverge on:
- Working directory context
- Environment variables (`SQUAD_TEAM_ROOT`, etc.)
- Registry path (`SQUAD_REGISTRY_PATH`)

**No test covers this divergence.** The guard gates side-effect initiation but does not enforce single-point resolution.
