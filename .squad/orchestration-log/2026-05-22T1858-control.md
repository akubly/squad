## Directive 1 — Exit-Code Derivation Must Be Exhaustiveness-Guarded

**File:** `packages/squad-cli/src/cli-entry.ts:1097–1102`

**Current code:**
```typescript
const warnCount = findings.filter(f => f.severity === 'warn').length;
const errorCount = findings.filter(f => f.severity === 'error').length;
if (errorCount > 0) process.exit(2);
```

**Problem:** The renderer's `switch(f.severity)` statement has a `never` arm for exhaustiveness. But this exit-code block uses `.filter()` with string literals — an open string comparison with no compile-time guard.

**Scenario:** If `DoctorSeverity` gains a new member (e.g., `'critical'`), the renderer will fail at compile time (correct). But this `.filter()` pattern will silently count `'critical'` findings as neither warn nor error, yielding exit code 0 when the process should exit 2.

**The inconsistency:** The two guards are not coupled at the type level. One is sound; one is unsafe.

**Fix:** Extract a typed `deriveExitCode` helper:
```typescript
function deriveExitCode(findings: DoctorFinding[]): 0 | 2 {
  for (const f of findings) {
    switch (f.severity) {
      case 'error': return 2;
      case 'warn':
      case 'info':
        break;
      default: {
        const _exhaustive: never = f.severity;
        throw new Error(`Unexpected severity: ${_exhaustive}`);
      }
    }
  }
  return 0;
}
```

**Priority:** Low urgency today (only 2 severity levels currently). High urgency when `DoctorSeverity` is extended.

## Directive 2 — `DoctorSource` Grouping Must Not Silently Drop Findings

**File:** `packages/squad-cli/src/cli-entry.ts:1085–1086`

**Current code:**
```typescript
const systemFindings = findings.filter(f => f.source === 'system');
const registryFindings = findings.filter(f => f.source === 'registry');
```

**Problem:** Any finding with a source that is neither `'system'` nor `'registry'` will be silently omitted from both groups and never rendered. Unlike the renderer's severity switch, there is no compile-time guard at the consumption site.

**Scenario:** A future third source (e.g., `'copilot'`) would produce findings that fall through both filter buckets and disappear. This is a silent data loss bug.

**Fix (preferred):** Add a post-grouping exhaustiveness assertion:
```typescript
const ungrouped = findings.filter(
  f => f.source !== 'system' && f.source !== 'registry'
);
if (ungrouped.length > 0) {
  const _exhaustive: never = ungrouped[0]!.source;
  throw new Error(`Unhandled doctor source: ${_exhaustive}`);
}
```

**Fix (alternative):** Switch to a Map-based dispatch:
```typescript
const bySource = new Map<DoctorSource, DoctorFinding[]>();
for (const f of findings) {
  switch (f.source) {
    case 'system':
      bySource.set('system', [...(bySource.get('system') ?? []), f]);
      break;
    case 'registry':
      bySource.set('registry', [...(bySource.get('registry') ?? []), f]);
      break;
    default: {
      const _exhaustive: never = f.source;
      throw new Error(`Unhandled source: ${_exhaustive}`);
    }
  }
}
```

**Priority:** Fix before adding a third `DoctorSource`.

## Directive 3 — `DoctorFinding` Fields Should Be `readonly`

**File:** `packages/squad-cli/src/cli/commands/doctor-types.ts`

**Current interface:**
```typescript
export interface DoctorFinding {
  severity: DoctorSeverity;
  label: string;
  message: string;
  source: DoctorSource;
  repair?: DoctorRepair;
}
```

**Recommended:**
```typescript
export interface DoctorFinding {
  readonly severity: DoctorSeverity;
  readonly label: string;
  readonly message: string;
  readonly source: DoctorSource;
  readonly repair?: DoctorRepair;
}
```

**Rationale:** `DoctorFinding` is a value object / diagnostic result. It represents the output of a health check and should not be mutated after construction. Mutation after construction has no valid use case, and allowing it can lead to subtle bugs if findings are cached or passed between layers.

`readonly` enforces the intent at the type level and prevents callers from patching findings mid-flow (e.g., changing severity after the fact).

**Priority:** Low-cost, high-clarity fix. Recommended for the next touch of this file. Not blocking.

## Non-Directives (Noted, Not Mandated)

1. **Two import paths for the same types:** `cli-entry.ts` imports `DoctorFinding` directly from `'./cli/commands/doctor-types.js'`; all other consumers import through the barrel. Recommend aligning to the barrel for consistency, but not a blocking concern.

2. **Batch severity on registry findings:** All registry findings receive the same severity (the max for the whole run). This is information-preserving given the old `RunDoctorResult` API shape. The design choice is acceptable and does not represent a type gap.

3. **`message: string` has no non-empty guard:** TypeScript cannot enforce non-empty strings without branded types. This is an accepted limitation.
