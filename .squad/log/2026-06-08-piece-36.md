## Residual Limitations (Accepted Per Spec)

### H — Sentinel Staleness Risk
The `.squad/.last-hydrate-sha` sentinel is keyed only on remote `fetchedSha`. If local TEAM_ROOT content drifts between two fetches of the same remote SHA, the idempotency guard silently skips re-hydration even though local content diverges from snapshot. **Per spec:** idempotency is a performance optimization only, not a correctness guarantee. **Mitigation:** Delete sentinel to force re-hydrate. **Future:** Key on `fetchedSha + hash(localSquadTree)` if content-drift detection becomes critical.

### I — Branch Uniqueness: Cross-Process Same-Millisecond Edge
Branch name generation uses millisecond-precision timestamp plus per-process monotonic counter. Within a process, same-millisecond uniqueness is fully guaranteed. Across multiple processes starting in the same millisecond with the same session ID, the counter resets independently per process, leaving a theoretical collision window. **Severity:** Low. **Accepted as low-risk given per-session entropy.**

### C — Hook Shell-Execution Non-Reentry: GitHub CI Follow-up
C1/C2 tests use a two-phase proxy (outer runSync publishes once; re-entrant with SQUAD_SYNC_ACTIVE pre-set asserts no second publish). This proves the logic is correct and install-hooks A2 asserts the hook template no longer pre-sets SQUAD_SYNC_ACTIVE. However, no test fires the real OS-level post-commit shell hook → `squad sync` subprocess and asserts that a sync-internal commit does NOT trigger a second publish cycle. **True end-to-end shell-hook test is flaky on Windows (timing/process isolation), runs reliably on Linux CI.** **Deferred as GitHub CI follow-up.**

## Lessons & Process Impact

### Why Adversarial Review Is Now Standard

**Incident:** CAPCOM's adversarial review (Opus model, assumed-wrong hypothesis) caught CRITICAL DEFECT-1 (double-`fold` template path) after FIDO's round 1 APPROVE. The defect would have shipped without this layer.

**Root Cause of Miss:** FIDO's acceptance gate verified test results (23 GREEN) and baseline integrity (0 regressions reported). However, EECOM's tests didn't exercise the actual published package structure — they passed locally but would fail in production. Adversarial review hunted for exactly this: **green-but-meaningless tests** and **correct-by-accident implementations**.

**Decision:** Adversarial peer review is now a **mandatory standard step** in piece replay reviews, in addition to primary Quality-Owner verification:
1. Core dev implements and triages (TDD, red→green)
2. **Quality Owner primary verification (FIDO)**
3. **NEW: Adversarial peer review by different agent + model (CAPCOM, CONTROL, etc.), assumed-wrong hypothesis**
4. If NO-GO, remediation is locked (core dev excluded) and handed to neutral engineer
5. Both QA + adversarial reviewer re-verify on amended commit before GO

This is a lightweight but mandatory peer-review pattern that leverages domain expertise and skeptical reasoning at the moment of highest confidence.
