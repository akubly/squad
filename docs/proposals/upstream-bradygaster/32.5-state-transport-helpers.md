# 32.5 — State transport helpers

## Summary

Define two parameterized transport helpers in `packages/squad-cli/src/cli/commands/sync.ts`:
`publishTeamRootToInbox` and `hydrateTeamRootFromStateRef`. These helpers are the per-developer
publication and hydration primitives consumed by piece 33's `runSync` push/pull wiring. Both
functions receive all resolution inputs as arguments; neither reads configuration files nor queries
the registry. Implementation uses the raw git plumbing pattern already established in `sync.ts`'s
existing private helpers (`execFileSync` from `node:child_process`).

Stack position: Part 32.5. Branches off piece 32 (`squad/piece-32-registry-state-fields`).
Foundation for piece 33's `runSync` push/pull wiring (33 sub-proposals B and C). Piece 33's
dependency line should read "branches off 32.5" rather than "branches off 32." Stack
re-sequences to: 32 → 32.5 → 33 → 34 → 35.

## Problem

Piece 33 (`sync-from-registry`) wires `runSync` to call `publishTeamRootToInbox` on the push path
and `hydrateTeamRootFromStateRef` on the pull path. Both functions are referenced by name in piece
33's verify-first probes and implementation sketches (sub-proposals B and C). Neither function
exists in the piece-32 lineage — verify-first probes against `squad/piece-32-registry-state-fields`
return line 0 for both (see Verify-first section). Piece 33's mandatory verify-first step requires
both exports to be present before implementation begins; if they are absent, piece 33's spec
instructs the implementer to stop.

The piece-32 implementation of `sync.ts` exports only two symbols: `SyncOptions` and `runSync`.
Its private helpers (`syncPull`, `syncPush`, `getRepoRoot`, `detectBackend`) provide the existing
single-repo sync primitives. The cross-repo transport layer — per-developer inbox publish and
TEAM_ROOT hydration — is a distinct concern that belongs in its own piece so that piece 33's
wiring step is cleanly separated from the helper definitions.

Two concrete gaps this piece closes:

1. **No per-developer publish primitive.** A cross-repo push requires creating a point-in-time
   snapshot of TEAM_ROOT `.squad/` content on a per-developer inbox branch on the docs remote.
   This operation does not exist in the piece-32 tree. Without it, a cross-repo push falls through
   to `syncPush`, which targets the code remote and pushes squad-state branches — incorrect
   behavior for the registry-first topology.

2. **No TEAM_ROOT hydration primitive.** A cross-repo pull requires materializing the docs
   remote's state branch into the TEAM_ROOT working directory. `syncPull` fast-forwards
   remote-tracking refs in the repo where it runs and does not touch TEAM_ROOT. The result is a
   stale TEAM_ROOT that never reflects the canonical state branch.

Both helpers must be present and exported before piece 33 can wire them into `runSync`.

## Proposed change

Define exactly two exported async functions in `packages/squad-cli/src/cli/commands/sync.ts`.
No other files in `packages/*/src/` are modified by this piece unless a session-shard path helper
is extracted to `packages/squad-sdk/src/` (see Changeset).

### A — `publishTeamRootToInbox`

**Signature (must match piece 33's call site exactly):**

```typescript
export async function publishTeamRootToInbox(
  teamRoot: string,
  remote: string,
  developerAlias: string,
  sessionId: string,
): Promise<void>
```

**Behavior:**

**Step 1 — Validate `developerAlias` before any git operation.**
Import `DEVELOPER_ALIAS_RE` from `@bradygaster/squad-sdk/validation` (established by piece 32,
accessible at that entry point per `packages/squad-sdk/package.json`). If `developerAlias` does
not match `/^[a-z][a-z0-9-]{1,38}$/`, exit with a descriptive error before creating any branch or
modifying any ref. Example message:
```
Invalid developerAlias "<value>": must match /^[a-z][a-z0-9-]{1,38}$/ (lowercase, starts with a letter, hyphens allowed, max 39 chars).
```

**Step 2 — Build the inbox branch name.**
The branch name format is:
```
squad/inbox/<developerAlias>/<yyyyMMdd-HHmmss>-<sessionId>
```
The timestamp is UTC. Derive it from `new Date().toISOString()`: extract the date and time
components and format as `yyyyMMdd-HHmmss` (digits only, no separators except the hyphen between
date and time). Example: `20260605-170543`.

**Step 3 — Resolve the base commit.**
In TEAM_ROOT, resolve the current `HEAD` SHA via `git rev-parse HEAD`. Record as `baseStateCommit`
in the metadata file.

**Step 4 — Build the snapshot using git plumbing.**
Enumerate all files under `TEAM_ROOT/.squad/` that match the allowlist. Write each file's content
into the TEAM_ROOT git object store with `git hash-object -w --stdin`. Build an in-memory index
via `git update-index --add --cacheinfo <mode>,<sha>,<path>` calls. Write the tree with
`git write-tree`. Create the commit with `git commit-tree <treeSha> -m "squad: publish snapshot"`.
All `execFileSync` calls use `cwd: teamRoot`.

**Snapshot allowlist (TEAM_ROOT `.squad/` subtree only):**

| Pattern | Files included |
|---------|---------------|
| `decisions.md` | `.squad/decisions.md` |
| `decisions/inbox/**` | `.squad/decisions/inbox/` and all descendants |
| `log/**` | `.squad/log/` and all descendants |
| `orchestration-log/**` | `.squad/orchestration-log/` and all descendants |
| `sessions/**` | `.squad/sessions/` and all descendants |
| `identity/**` | `.squad/identity/` and all descendants |

**Allowlist guard (hard requirement):** Before staging any file, enumerate every path that would be
included. If any resolved path falls outside the above allowlist, exit with an error message
identifying the violating path. No product-repo files and no `.squad/` files outside the allowlist
may appear in the snapshot commit. This guard is the in-code enforcement point for "no squad files
in product PRs" — paths that escape it could appear in a downstream fold and pollute upstream diffs.

**Step 5 — Write `.squad/publish-metadata.json` into the commit.**
Include the metadata file as an additional entry in the tree before calling `git write-tree`.
Content:

```json
{
  "developerAlias": "<developerAlias>",
  "sessionId": "<sessionId>",
  "sourceWorkRoot": {
    "repo": "<basename of process.cwd() or teamRoot parent>",
    "pathHash": "sha256:<hex of sha256 of normalized abs path>"
  },
  "publishedAt": "<ISO-8601 UTC with Z suffix>",
  "baseStateCommit": "<sha>"
}
```

`publishedAt` is `new Date().toISOString()` — always UTC with a `Z` suffix. `baseStateCommit` is
the SHA from step 3.

**§9 NFR PII rule (non-negotiable):** `sourceWorkRoot` is an object with exactly two fields:
`repo` (the basename of the work-tree directory, not an absolute path) and `pathHash`
(`"sha256:"` + the lowercase hex SHA-256 digest of the normalized absolute path). Normalization:
lowercase, forward-slash-separated, no trailing slash. Use `node:crypto`'s `createHash('sha256')`
with `update(normalizedPath).digest('hex')`.

**Raw absolute paths must not appear in any string field of `publish-metadata.json`.** This
includes strings containing `Users\`, `/home/`, drive-letter prefixes, or any other OS
user-directory segment. The `pathHash` form preserves cross-clone debugging signal (two clones at
the same path produce identical hashes; two clones at different paths do not) without exposing
OS-level identity. Any `publish-metadata.json` with a string `sourceWorkRoot` or with raw absolute
path segments fails the scrub gate introduced in piece 30.5 Gate 7.

**Step 6 — Push the inbox branch.**
```
git push <remote> <commitSha>:refs/heads/<inboxBranch>
```
The inbox branch is new for every session; no non-fast-forward conflict is possible. Concurrent
publishes from separate developers produce independent `squad/inbox/<alias>/…` refs with no
structural relationship.

**Implementation note:** All git operations in sub-proposal A use `execFileSync('git', […])` with
`cwd: teamRoot`, matching the existing private-helper pattern in `sync.ts`. `OrphanBranchBackend`
is not present in this lineage and must not be assumed. The private `getRepoRoot` helper already in
`sync.ts` may be reused if TEAM_ROOT's git root needs resolution.

### B — `hydrateTeamRootFromStateRef`

**Signature (must match piece 33's call site exactly):**

```typescript
export async function hydrateTeamRootFromStateRef(
  teamRoot: string,
  remote: string,
  stateBranch: string,
): Promise<void>
```

**Behavior:**

**Step 1 — Fetch the state branch.** In the TEAM_ROOT context:
```
git fetch <remote> refs/heads/<stateBranch>:refs/remotes/<remote>/<stateBranch>
```
If the ref does not exist on the remote, surface a clear error rather than silently no-opping.

**Step 2 — Resolve the fetched SHA.**
```
git rev-parse refs/remotes/<remote>/<stateBranch>
```

**Step 3 — Idempotency check.** Resolve TEAM_ROOT's current working-directory HEAD via
`git rev-parse HEAD` (cwd: teamRoot). If the result equals the fetched SHA from step 2, return
without further action — TEAM_ROOT is already current.

**Step 4 — Check out the tree.** Materialize the fetched commit's tree into TEAM_ROOT:
```
git --work-tree=<teamRoot> checkout refs/remotes/<remote>/<stateBranch> -- .
```
This writes the state branch's file tree into TEAM_ROOT's working directory without altering
TEAM_ROOT's `HEAD` pointer. Operates on TEAM_ROOT only — no writes to WORK_ROOT or any other path.

**Implementation note:** Same `execFileSync` pattern as sub-proposal A. No side effects outside
TEAM_ROOT.

### C — Parameterization contract

Both helpers are **parameterized transport primitives**. They accept fully resolved inputs as
arguments and must not perform any of the following:

- Read `config.json` from any path.
- Load or query the squad registry.
- Call `detectBackend()` or any config-reading helper.
- Read environment variables for input resolution (env-var fallback is piece 33's responsibility).

This keeps piece 32.5 topology-agnostic. The caller (piece 33's `runSync`) owns all resolution.

### §9 NFR PII guard

`publish-metadata.json` must never contain a raw absolute path string. The `sourceWorkRoot` field
is always an object (not a string). Its `pathHash` is SHA-256 of the normalized absolute path. Two
invocations from the same work-tree root produce the same `pathHash`. Two invocations from
different roots produce different hashes. Any serialized `publish-metadata.json` whose
`sourceWorkRoot` is a string, or whose any field contains path segments matching
`(Users|home)[/\\]`, fails piece 30.5's scrub Gate 7.

### Snapshot allowlist guard

The allowlist is the in-code enforcement point for "no squad files in product PRs." If any staged
path resolves outside the allowlist, `publishTeamRootToInbox` exits with a descriptive error before
any git commit object is created. This prevents accidental inclusion of product source files,
changelogs, or root-level `.squad/` files (e.g., `config.json`, `team.md`) in the inbox snapshot.

## Deployer constraints honored

1. **GitHub AND ADO both supported.** The `remote` parameter is a git remote name, not a URL.
   Platform resolution (GitHub vs. ADO) is determined by the remote's configured URL, handled by
   `packages/squad-sdk/src/platform/detect.ts`. Piece 32.5 contains no platform-specific logic.

2. **No `.gitignore` or `.git/info/exclude` writes.** Neither helper modifies any ignore file at
   any path.

3. **No product-repo writes.** Both helpers operate exclusively on TEAM_ROOT and the docs remote.
   `hydrateTeamRootFromStateRef` checks out files into TEAM_ROOT. `publishTeamRootToInbox` stages
   content from TEAM_ROOT and pushes to the docs remote. Neither function has a code path that
   touches WORK_ROOT.

4. **State publication only through helper push, never product-repo automation.** The only
   mechanism by which state reaches the remote is the explicit `git push` inside
   `publishTeamRootToInbox`. No CI pipeline, no post-push hook in the product repo, and no
   background sync process is introduced by this piece.

5. **User-scoped precedent.** Both helpers operate on TEAM_ROOT and a named remote, consistent with
   `squad assign`'s user-scoped model. The docs-repo clone (TEAM_ROOT) is the user's sidecar;
   `remote` names the remote within that clone. The helpers carry no per-product-repo configuration.

## Test surface

Target file: `test/cli/cross-repo-sync.test.ts` (new). Tests exercise the two helpers directly
against bare-repo fixtures — NOT via `runSync`. Piece 33 owns the `runSync` integration surface;
piece 32.5's tests verify the helpers themselves.

| # | Test | What it verifies |
|---|------|-----------------|
| 1 | Two developers publish concurrently to the same bare remote | No non-fast-forward conflict. Each developer's inbox ref is independent: `squad/inbox/dev1/…` and `squad/inbox/dev2/…` are created without error. |
| 2 | `hydrateTeamRootFromStateRef` round-trip on a synthetic state commit | A fresh TEAM_ROOT working directory receives the correct file tree from the state branch after hydration. |
| 3 | `publish-metadata.json` has object-shaped `sourceWorkRoot` | The published commit's metadata parses to an object with `repo` (string) and `pathHash` (string starting with `"sha256:"`). |
| 4 | Raw absolute path absent from `publish-metadata.json` | No string value in the serialized JSON contains OS user-directory segments (`Users\`, `/home/`, drive-letter prefixes). |
| 5 | `pathHash` stable across two invocations from the same work-tree | Two separate calls from the same TEAM_ROOT path produce identical `pathHash` values. |
| 6 | `hydrateTeamRootFromStateRef` is idempotent | Calling the function twice when TEAM_ROOT is already at the fetched commit is a no-op (no error, no redundant git operations on the second call). |
| 7 | Missing or malformed `developerAlias` exits before creating a branch | Calls with `developerAlias = ""`, `"BAD"`, `"-abc"`, or a 40-character string exit before any ref is created on the bare remote. |
| 8 | A staged path outside the allowlist causes publish to error | A TEAM_ROOT containing `.squad/config.json` (outside the allowlist) causes `publishTeamRootToInbox` to exit with an error before any commit object is created. |
