Test regressions accumulated through the doctor cleanup arc. This piece ships a single squashed commit closing the fork-introduced regressions so subsequent pieces start from a fully green baseline — modulo a small set of acknowledged upstream-inherited failures that also fail on `origin/dev`.

Stack position: Part 25.5 of the upstream-bradygaster effort. Branches off piece 25 (`squad/piece-25-resolver-rename-and-cli-hardening`). Foundation cleanup before the new cross-repo arc (piece 32+). The 0.5 suffix signals "regression repair, not a feature piece."

## Problem

At the piece 25 branch tip, `npx vitest run` reports approximately 32 failing tests across 16 files. After comparison against `origin/dev`, the failures separate cleanly into two populations:

**Upstream-inherited (also fail on `origin/dev`) — 5 tests, out of scope:**

- `acceptance` → Init command: Init in existing project shows ready message
- `team-root-resolution` → invalid SQUAD_TEAM_ROOT path → resolveSquad returns null

**Fork-introduced regressions — in scope:**

The in-scope failures span approximately 10 files confirmed by sampling and an undetermined number of additional files. The full enumeration is an open task for the implementer (sub-proposal G). Confirmed in-scope failures include:

- 2 in `test/ralph-commands.test.ts` — Planner platform commands
- 2 in `test/cli-command-wiring.test.ts` — unwired command files in `cli-entry.ts`
- 2 in `test/sdk-feature-parity-batch3.test.ts` — platform detection fallback values
- 4 in `test/acceptance/acceptance.test.ts` — Doctor output format (3) and Consult precondition (1)
- 2 in `test/acceptance/hostile.test.ts` — Doctor exit code at 40×10 and without `.squad/`
- 1 in `test/cli/register.test.ts` — fork-only test file
- 3 in `test/cli/dispatch-help.test.ts` — Doctor output format and exit code

The most consequential pattern among the in-scope failures: command files exist in `packages/squad-cli/src/cli/commands/` but are never imported in `cli-entry.ts`. The `test/cli-command-wiring.test.ts` suite was added precisely to catch this defect class. At the piece 25 tip, `doctor-types.ts` and `init-remote.ts` are both unwired. This is the same defect class — a command file exists but users cannot reach it — that surfaced as the primary cross-repo arc failure in piece 31. Closing it at the foundation prevents recurrence in the new chain.

## Proposed change

### A — CLI command wiring repair

**Failing tests:**

- `test/cli-command-wiring.test.ts` → `commands/doctor-types.ts is imported in cli-entry.ts`
- `test/cli-command-wiring.test.ts` → `commands/init-remote.ts is imported in cli-entry.ts`

**Affected source:**

`packages/squad-cli/src/cli-entry.ts`

**Fix shape:**

`doctor-types.ts` (`packages/squad-cli/src/cli/commands/doctor-types.ts`) is a types-only module exporting `DoctorFinding`, `DoctorSeverity`, `DoctorSource`, and `DoctorRepair`. It is never imported from `cli-entry.ts` directly, though `cli-entry.ts` uses `DoctorFinding[]` in the unified doctor section (lines ~1054–1079). Add a static `import type` from `'./cli/commands/doctor-types.js'` at the top of `cli-entry.ts` alongside the existing SDK and core imports.

`init-remote.ts` (`packages/squad-cli/src/cli/commands/init-remote.ts`) exports `writeRemoteConfig(projectDir, teamRepoPath)`. The `init --mode remote` branch in `cli-entry.ts` parses `remoteTeamPath` (line ~356) and validates its presence (line ~358) but never calls `writeRemoteConfig`. Add a dynamic `import('./cli/commands/init-remote.js')` inside the `mode === 'remote'` branch and call `writeRemoteConfig(resolvedTargetDir, remoteTeamPath)` after the standard `runRegistryInit` call.

**Acceptance criteria:** Both wiring tests transition RED → GREEN.

### B — Doctor output header and exit-code repair

**Failing tests:**

- `test/cli/dispatch-help.test.ts` → `squad doctor runs and exits 0 on clean state` (expects `System doctor`, `Registry doctor` in stdout)
- `test/cli/dispatch-help.test.ts` → `labels System doctor and Registry doctor sections` (same)
- `test/cli/dispatch-help.test.ts` → `exits 0 when registry has only info-level findings` (expects exit code 0)
- `test/acceptance/features/doctor-extended.feature` → `Doctor shows diagnostic header` (expects `Squad Doctor` in output)
- `test/acceptance/features/doctor-extended.feature` → `Doctor shows summary with pass count` (expects `Summary:` in output and `\d+ passed` pattern)
- `test/acceptance/features/doctor.feature` → `Run doctor in project with squad setup` (expects exit code 0)
- `test/acceptance/features/hostile-tiny-terminal.feature` → `Doctor command works at 40x10` (expects exit code 0)
- `test/acceptance/features/hostile-no-config.feature` → `Doctor runs without .squad/ directory` (expects exit code 0)

**Affected source:**

`packages/squad-cli/src/cli-entry.ts`, unified doctor section (~lines 1052–1079)

**Fix shape:**

Two independent issues are co-located in the unified doctor render block:

*Header text:* The current render block outputs `=== System ===` and `=== Registry ===` as section labels. Tests expect `System doctor` and `Registry doctor`. Update the two `console.log` calls at the section boundaries. Add a `Squad Doctor` header before the section output (the `cli/commands/doctor.ts` `printDoctorReport` function prints `🩺 Squad Doctor` — the acceptance test expects `Squad Doctor`; use a plain-text prefix compatible with `NO_COLOR`). Prefix the final summary count line with `Summary:` (currently the line reads `N passed, M errors, K warnings` with no `Summary:` prefix).

*Exit code:* `deriveExitCode` returns `2` for any error-severity finding, including system-level findings such as missing `.squad/` directory. Tests that run the doctor in directories without `.squad/` expect exit code `0` — the doctor is a diagnostic tool, not a gate. The fix is to apply `deriveExitCode` only to registry-sourced findings. System findings should never drive a non-zero exit. Update the `process.exit(2)` guard at line ~1077 to filter `findings` to `source === 'registry'` before calling `deriveExitCode`.

**Acceptance criteria:** All 8 listed tests transition RED → GREEN. The `squad doctor --help` test (line ~87 in dispatch-help.test.ts) must remain GREEN — it should not output `System doctor` content.

### C — Consult precondition message repair

**Failing test:**

- `test/acceptance/features/consult-command.feature` → `Consult in non-git directory fails` (expects `Not a git repository` in output, exit code 1)

**Affected source:**

`packages/squad-cli/src/cli-entry.ts`, consult section (~lines 1081–1096)

**Fix shape:**

The consult handler currently resolves the squad directory and emits `'No squad found.'` when resolution fails. The test runs `squad consult` in a temp directory that has no `.squad/` and is not a git repository. The test expects `Not a git repository`, not `No squad found`.

The fix is to check whether the current working directory is inside a git repository before checking for squad resolution. If the git check fails (e.g., `git rev-parse --git-dir` exits non-zero), emit `'Not a git repository'` and exit 1. The existing squad resolution check follows only when git is present. The git check can use `existsSync` against the `.git` directory tree or `execSync`; either approach is acceptable so long as it covers the case where the temp dir is not inside any git tree.

**Acceptance criteria:** The `Consult in non-git directory fails` scenario transitions RED → GREEN. The `Consult blocked in squadified project` and `Consult --status` scenarios must remain GREEN.

### D — Ralph commands Planner routing

**Failing tests:**

- `test/ralph-commands.test.ts` → `planner platform` → `uses Graph API via az token for planner tasks`
- `test/ralph-commands.test.ts` → `planner platform` → `indicates PRs are not managed by Planner`

**Affected source:**

`packages/squad-sdk/src/platform/ralph-commands.ts`, `getRalphScanCommands` function (~line 26)

**Fix shape:**

The `switch` in `getRalphScanCommands` has cases for `'github'` and `'azure-devops'` only. The `'planner'` case falls through to the `default` branch, which returns GitHub commands. `getPlannerRalphCommands()` already exists at line ~37 and returns the correct Graph API commands. Add `case 'planner': return getPlannerRalphCommands();` to the switch.

**Acceptance criteria:** Both planner-platform tests transition RED → GREEN. The `default platform fallback` test (falls back to GitHub for unknown platform) must remain GREEN.

### E — SDK platform detection fallback values

**Failing tests:**

- `test/sdk-feature-parity-batch3.test.ts` → `detectPlatformFromUrl` → `defaults to github for unrecognized URL`
- `test/sdk-feature-parity-batch3.test.ts` → `detectWorkItemSource` → `falls back to platform detection when config is undefined`

**Affected source:**

`packages/squad-sdk/src/platform/detect.ts`

**Fix shape:**

`detectPlatformFromUrl` (line ~134): the current default return is `'unknown'`. The test at line ~413 calls `detectPlatformFromUrl('https://gitlab.com/owner/repo')` and expects `'github'`. Change the final `return 'unknown'` to `return 'github'`.

`detectWorkItemSource` (line ~208): the catch block returns `'unknown'` when `detectPlatform` throws. The test at line ~424 calls `detectWorkItemSource('/tmp/nonexistent')` (no git remote available) and expects the result to be one of `['github', 'azure-devops', 'planner']`. `'unknown'` is not in that set. Change `return 'unknown'` in the catch to `return 'github'`.

The `PlatformType` type in `types.ts` may include `'unknown'` as a value. Verify that changing the fallback does not require a type-system update; if `PlatformType` carries `'unknown'`, the return type annotation on `detectPlatformFromUrl` may also need narrowing. Use implementer judgment.

**Acceptance criteria:** Both detect-* tests transition RED → GREEN. All existing `parseGitHubRemote`, `parseAzureDevOpsRemote`, and platform-specific tests must remain GREEN.
