# 30.5 — Scrub-gate cross-surface audit

## Summary

One-shot audit of `_scrub-gate.ps1` adding three cross-cutting gate rules required by the new surfaces introduced in pieces 26–30. All three rules are `[upstream-bound]` — they protect product surfaces shipped by the arc and flow upstream with the feature. The existing gates 1–6 are not modified by this piece.

Stack position: Part 30.5 of the cross-repo arc. Depends on pieces 26–30 (all surfaces must be present). The 0.5 suffix signals "additive gate audit, not a feature piece." Branch off `squad/piece-30-ado-cross-repo-templates`.

## Problem

Pieces 26 (config), 28 (publish-metadata), and 30 (ADO templates) introduce three tree surfaces that need cross-cutting protection, and adding rules piecemeal during those pieces creates regression coupling:

- A Gate 7 rule added in piece 26 could flag piece 30's ADO template syntax before piece 30 lands Gate 8's exclusion.
- A Gate 9 alias-format rule added in piece 26 could fail on a fixture in piece 28 before piece 28 locks the alias schema.

A single atomic audit after all surfaces from 26–30 are known avoids mid-arc breakage and ensures all three rules are coherent with each other.

The three unprotected surfaces:

1. `.squad/config.json` and `.squad/publish-metadata.json` may contain absolute paths with user identity segments if `sourceWorkRoot` or any derived field is mis-implemented. The scrub gate has no rule that catches this.
2. `.squad-templates/ado/**` files legitimately contain ADO variable syntax (`$(System.AccessToken)`, `$(Build.SourcesDirectory)`). Gate 4's internal-reference check may false-positive on files that include the word `internal` (a common term in ADO pipeline documentation), and a future tightening of Gate 4 into a generic secret scanner would flag these patterns without an explicit exclusion.
3. `developerAlias` in config or publish-metadata has no format validation in the gate, allowing malformed aliases (uppercase letters, email-style with `@`, length over 39) that would corrupt inbox branch names.

## Gate flavor

All three new rules in this piece are `[upstream-bound]`. They protect product surfaces shipped by the cross-repo arc. They belong in the upstream product's gate infrastructure, not in replay-private isolation guards.

The existing gates 1–6 are out of scope for this piece. Their classification — `[upstream-bound]` for commit-hygiene gates or `[replay-private]` for isolation guards — is a separate concern and does not block this piece.

Authoring rule: every gate-rule addition must carry either `# [upstream-bound]` or `# [replay-private]` as a comment immediately above its rule body. The three new rules below carry `# [upstream-bound]`.

## Proposed change

Add Gates 7, 8, and 9 to `_scrub-gate.ps1`. Each rule is preceded by a `# [upstream-bound]` comment. Existing gates 1–6 are not modified.

### Gate 7 — No user-path segments in config/metadata strings `[upstream-bound]`

Scan `.squad/config.json` and `.squad/publish-metadata.json` (when present in the tracked tree) for any string value matching `(Users|home)[/\\]`. Skip silently if neither file is tracked.

Failure message:

```
Gate 7 FAIL: raw user-path segment detected in {file}; use {repo, pathHash} structure (see piece 28 spec §9 NFR annotation)
```

Implementation: `git grep -E '(Users|home)[/\\]'` restricted to the two target files. No false positive on `.squad/agents/` or other `.squad/` subdirectories.

### Gate 8 — ADO variable syntax allowed in `.squad-templates/ado/**` `[upstream-bound]`

Scan files under `.squad-templates/ado/` for `$(...)` expressions. Assert that every such expression matches the ADO variable name pattern `[A-Za-z][A-Za-z0-9._]*`. Skip silently if no ADO template files are tracked.

The gate **passes** when all `$(...)` expressions are well-formed ADO variable references, making `$(System.AccessToken)` and `$(Build.SourcesDirectory)` explicitly safe. The gate fails only if a `$(...)` expression contains a value that does not match the ADO variable name pattern (potential injection or misuse).

Failure message:

```
Gate 8 FAIL: non-ADO $() expression in {file}: {expression} — use $(VariableName) ADO runtime syntax only
```

### Gate 9 — `developerAlias` format validation `[upstream-bound]`

When `.squad/config.json` or `.squad/publish-metadata.json` is present in the tracked tree and contains a `developerAlias` field, assert the value matches `^[a-z][a-z0-9-]{0,38}$`. Skip silently if neither file is tracked or if neither contains `developerAlias`.

Failure message:

```
Gate 9 FAIL: developerAlias must match [a-z][a-z0-9-]{0,38} (lowercase letters, digits, hyphens; starts with letter; max 39 chars) in {file}: '{value}'
```

Implementation: read each tracked config file from disk, extract `developerAlias` with a regex capture, validate the extracted value against the pattern. A file with no `developerAlias` key passes.

## Test surface

New `test/scrub-gate-surfaces.test.ts`. Tests invoke `_scrub-gate.ps1` against synthetic fixture trees, not the live working tree. Each fixture is a purpose-built directory containing only the files relevant to the rule under test. The test harness runs the gate against each fixture and asserts the exit code and relevant failure message.

Fixture set:

**Gate 7 — user-path segment**

Fixture (a): `config.json` containing a string value with a user-path segment. Expected: Gate 7 FAIL.

```json
{ "sourceWorkRoot": "C:\\Users\\dev1\\src\\monorepo" }
```

Fixture (b): `config.json` containing only a structured `sourceWorkRoot` with no user-path segment. Expected: Gate 7 PASS.

```json
{ "sourceWorkRoot": { "repo": "monorepo", "pathHash": "sha256:abc" } }
```

**Gate 8 — ADO variable syntax**

Fixture (c): A file in `.squad-templates/ado/` containing `$(System.AccessToken)`. Expected: Gate 8 PASS.

**Gate 9 — alias format**

Fixture (d): `config.json` with `"developerAlias": "Alice"` (uppercase initial). Expected: Gate 9 FAIL.

Fixture (e): `config.json` with `"developerAlias": "alice-1"`. Expected: Gate 9 PASS.

**Non-regression**

Fixture (f): A fixture tree containing only `.squad/agents/` files (no config, no metadata, no ADO templates). Expected: Gates 7, 8, and 9 all skip or pass — no false positives on non-target files.

All fixtures exercise the gate in isolation. No fixture includes live repo content. The existing gate behavior on `.squad/agents/` files (Gates 1–6) must not regress — verified by running the full gate on the live working tree as a separate assertion at the end of the test suite.

## Implementation note

This piece ships both the gate code additions to `_scrub-gate.ps1` and the new test file `test/scrub-gate-surfaces.test.ts` in the same commit. The three gate rules and the test fixtures are co-developed: write a failing fixture first, implement the gate rule, confirm the fixture passes. The gate additions do not modify any existing gate function; they append after Gate 6.
