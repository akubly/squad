Fix piece-56 §B bulk managed hydrate silently no-opping on the real cold-start path (regression of decision G1). §B had **two** independent defects; both are fixed here:

- **Gate keyed on the wrong signal.** `hydrateTeamRootFromRef` gated its bulk unfiltered `git fetch` on `remote.<remote>.promisor === true`, keyed on the remote *token* the caller threads. But `git clone --filter=blob:none` records the promisor flag under the clone's own remote **name** (`origin`), while `assign` threads the resolved state/config remote token — a URL or a distinct remote name such as `squad-config` — so the name-keyed lookup missed, the bulk fetch was skipped, and the per-file `cat-file blob` loop fell back to O(files) promisor fetches (a ~1,600-file cold-start took ~41 min). The partial clone is now detected **remote-agnostically** by scanning `git config --get-regexp '^remote\..*\.promisor$'` for any `true`, so the single blob-materializing fetch fires regardless of which token the hydrate is driven with. A full clone has no promisor remote, so non-managed `--pull` stays byte-identical (no extra network); the `.last-hydrate-sha` fast-path skip ordering and monorepo `--absolute-git-dir` handling are unchanged.
- **Bulk fetch no-opped on the already-present ref.** Even with the gate firing, `git fetch --no-filter <remote> <refspec>` backfilled **zero** blobs: the ref's commit was already present from the earlier filtered fetch, so git's commit-based negotiation reported "up-to-date" and `--no-filter` did not retroactively hydrate the skipped blobs. The `cat-file` write-out then lazily promisor-fetched every blob individually (O(files), inside the `cat-file` subprocess), so the cold-start stayed ~41 min. The bulk fetch now uses `git fetch --refetch --no-filter <remote> <refspec>`, which ignores negotiation and backfills all lane blobs in one transfer (verified: 0 blobs on a plain `--no-filter` re-fetch vs 1055 with `--refetch`; live cold-start dropped 2482 s → 305 s with zero cycling git children). The fast-path skip ordering is preserved.
- **Cost model (corrected wording).** §B collapses the write-out's network cost to a **single bulk fetch invocation per lane** — O(1) child processes, not the O(files) per-blob spawns it replaces. It is *not* O(1) bytes: because `--refetch` disables negotiation it re-transfers the tip's full reachable blob set on each **changed-tip** hydrate (O(snapshot) bytes per changed tip, not a delta). This is the intended trade for eliminating the O(files) round trips; the `.last-hydrate-sha` sentinel keeps unchanged-tip re-pulls free, and git's auto-gc/repack reclaims the duplicate packs `--refetch` leaves behind so `.git` stays bounded.
- **`--refetch` requires git ≥ 2.36; the fast path is now best-effort.** Partial clones exist since git 2.19, but `git fetch --refetch` only since 2.36. On an intermediate git the bulk fetch would error on the unknown option. Rather than hard-fail a managed cold-start that previously succeeded (slowly), a bulk-fetch failure is now **non-fatal**: it is logged (`console.warn`) and the hydrate falls back to the per-blob lazy path — the exact pre-optimization behavior. Managed hosts should still run git ≥ 2.36 for the fast path (already implied by `docs/.../cross-org-auth.md`).
- The §B regression test now (a) drives the hydrate with a remote token that is NOT the clone's promisor remote name (the production calling convention) and asserts the network-touching fetch count is O(1) per lane, independent of file count; (b) models git's fetch/`cat-file` object semantics through the git-exec seam to assert the `cat-file` write-out performs **zero** lazy promisor fetches after §B's bulk fetch *and* that the bulk fetch targets the correct driving remote token and lane refspec — a cost/target an exec-call counter cannot see because it happens inside the `cat-file` subprocess; and (c) asserts a bulk-fetch failure is non-fatal and the hydrate still materializes every file via the lazy path. All fail on the pre-fix code and pass with the fixes.
